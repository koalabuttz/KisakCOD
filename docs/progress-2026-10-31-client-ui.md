# Native UI image commands and layered material resources

The Linux CPU renderer now runs an actual existing UI caller chain: `UI_DrawHandlePic` → `CL_DrawStretchPic` → `ScrPlace_ApplyRect` → `CL_DrawStretchPicPhysical` → the CPU implementation of `R_AddCmdDrawStretchPic`. Identical SP/MP client wrappers were extracted into one shared file. The real UI and screen-placement translation units compile and execute; standalone input globals now use the production screen-placement owner. This is a bounded unlit image capability, not initialization of the complete game menu, asset database, font renderer, cgame, audio or CL_Frame.

The normal game renderer retains its original material technique/depth validation and fallback behavior. Both implementations share stretch-picture command emission and the unchanged actual `R_ConvertColorToBytes` packing implementation, now in a narrow shared source. Common game and explicit Radiant source lists include the new shared files where applicable. The CPU entry is deliberately selected at link time; it does not set game renderer registration flags or pretend to implement arbitrary shaders.

CPU UI materials explicitly bind an owned image. Monotonic material handles survive restart without reuse; releasing a texture referenced by a material fails. Registration and release require ready state, and recording/pending resources are immutable. `DrawUiImage` scopes a renderer, handle and exact expected material identity around the real UI call. The backend rejects calls outside that scope or with an unexpected pointer before dereferencing it. Command-offset/material-handle sidecars authorize internal replay; external stretch-picture command lists always reject. Explicit normal/catch cleanup restores the scope on standalone exceptions. It does not claim to unwind a legacy game Com_Error longjmp.

The supported policy is bilinear sampling with clamped normalized UVs, actual engine packed tint, and source-alpha/inverse-source-alpha RGB blending onto an opaque target. Pixel centers map to source texel centers with `u*width-0.5`; UV reversals generated by the real UI negative-width/height behavior are supported. With sampled channel C, sampled alpha A, packed tint channel T and tint alpha Ta, source RGB is C*T/255, opacity is A*Ta/(255*255), and output RGB is rounded-to-nearest `source*opacity + destination*(1-opacity)`; output alpha is 255. This explicit policy does not promise all game material state combinations. Finite geometry is bounded before coordinate conversion, UVs are normalized, colors are checked before packing, and clipped iteration never extends beyond the framebuffer.

The existing window/input host uploads a 64x64 image and invokes the real UI caller to render it at 128x96, with white tint and half alpha (packed 128), over its existing color clear. This changes the actual rendering path rather than adding a separate demo executable. Trace provenance is `presentation=engine-ui-image` and `producer=UI_DrawHandlePic`. X11 verification uses independent analytic expected colors, including bilinear transition samples, alpha blending, exact rectangle boundaries and untouched background.

Focused runtime coverage verifies actual virtual screen placement, physical alignment, negative-width UV reversal, independently calculated interpolation/tint values, clipping, huge/nonfinite input rejection, restored scope after an error, and external/unscoped material rejection without partial mutation. Allocation tests cover material object/map-node failure, retained texture ownership, release/restart, stale handles and pending teardown. Layered material construction is a separate production resource fix with MP/SP/Radiant variants; its helper-boundary fixtures do not claim shader/device execution.

Ordinary asset Material pointers are not registered CPU materials and cannot enter without the explicit scoped binding. Supported resources are owned RGBA8 images with the stated unlit/bilinear-clamp/source-over policy. IWI/DDS loading, compressed/volume/cubemap resources, arbitrary shader techniques, depth, font/text rendering, rotated pictures and arbitrary quad geometry remain unsupported.
