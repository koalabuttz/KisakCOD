# Linux CPU renderer command and resource lifecycle

This checkpoint connects the existing Linux input/window host to a narrow production rendering path: the engine's actual `GfxCmdArray`, `GfxCmdHeader`, `GfxCmdClearScreen`, clear/end command producers, and `Byte4PackRgba` color conversion. Its CPU backend supports full-surface color clears and end-of-list only. It does not initialize D3D9, materials, world geometry, depth/stencil, audio, full `R_Init`, or `CL_Frame`, and never sets renderer-registered or connected state to suggest otherwise.

The shared `r_command_buffer` implementation now backs both the original game wrappers and the explicit Linux command context. Game frame-state assertions, warning thresholds and critical-command reserve policy remain in their original wrapper. The explicit allocator checks its storage metadata before pointer arithmetic. Physical capacity cannot be enlarged by critical usage exceeding the reserve: the old subtraction could become negative and grant nonexistent space to later noncritical commands; the shared allocator clamps the remaining reserve at zero and the regression covers that boundary. Command IDs and structure layouts remain the existing engine definitions, including Radiant conditional IDs.

`CpuRenderer` owns its aligned command storage and CPU pixel resource. Initialize is transactional; resize failure preserves resources and recorded/pending work; a successful resize cancels work tied to the old dimensions. Begin/clear/submit/present enforce lifecycle states, reject a second pending frame, and never retain external command storage. Submission validates the entire list before mutating pixels, so unsupported or malformed tails cannot partially execute a clear. Depth/stencil or drawing commands fail explicitly. Finite colors are clamped before the actual engine RGBA packer; nonfinite colors reject before conversion. Presentation consumes pending work only after SDL succeeds. Shutdown/destruction discard recording or pending work and release resources; restart begins with fresh accounting.

The existing `KisakCOD-client-input` executable now generates an engine color-clear command instead of diagnostic quadrant artwork. Its trace identifies `presentation=engine-color-clear` and `producer=R_EmitClearScreenCommand`. The visible RGB is (64,128,191), obtained from engine conversion of (0.25,0.5,0.75,1). This demonstrates the supported rendering command subset, not game scene rendering. The separate pixel-presentation fixture retains exact asymmetric/padded pixel coverage. Window resize, event input, frame-deadline pacing and teardown continue through the existing host.

Build with `KISAK_BUILD_LINUX_WINDOW_HOST=ON` and the existing matching 32-bit SDL2 SDK. New focused targets are `KisakCOD-cpu-renderer-test` and `KisakCOD-cpu-renderer-fault-test`; the latter injects allocation failures only in its isolated test executable through global allocation overrides. No production fault hook or fallback success is introduced. Both are integrated into `scripts/tests/test_linux_window.py`. Evidence is retained in `/workspace/kisakcod-client-render-lifecycle-results`.

The initial basic fixture accidentally reused its serialized frame storage for an allocator-reserve test; the resulting later command rejection was fixed by separating those test buffers. An initial smoke run also used the old trace expectation before the checker update. Neither initial failure is counted as a passing result; final reruns use the corrected fixture and checker.

No packet, receive, authentication or network implementation is changed. The prior packet action remains denied by the automated agent cybersecurity-risk check, not an exec approval, and has not been retried. Exact blocker: `/workspace/kisakcod-client-input-startup-results/packet-work-blocker.json`. Prior combined server/client evidence remains `/workspace/kisakcod-integration-check-results/REPORT.md` for its recorded snapshot; it does not establish this new renderer delta. The independent server patch remains `/workspace/kisakcod-refill-results/server-cumulative.patch`.

Focused final coverage includes actual producer/layout and critical-reserve behavior, different-color clear followed by an unsupported tail with full pixel/state/count preservation, valid-list depth rejection, truncated end, second-pending rejection, same-size resize cancellation, actual SDL presentation, failed closed-window presentation preserving pending work, and repeated shutdown/restart. The independent allocation fixture covers initial and resize `bad_alloc`, retained recording after failure, successful retry, and destruction of pending resources without leaks.

The legacy renderer command ownership regression passes all eight scenarios after extraction. Full `r_rendercmds.cpp` MP and Radiant translation-unit checks remain **unverified**: both current and baseline `b8abbd43` fail at the pre-existing Linux incomplete `IDirect3DSurface9::Release` dependency; Radiant additionally fails its `Material` size assertion under that configuration. No fabricated graphics SDK or unrelated platform workaround was used. Logs `legacy-rendercmds-*-compile.log` preserve both baseline and current failures. This limitation does not prevent compiling/executing the actual extracted shared producer in the supported Linux targets, but it limits claims about complete Windows/Radiant renderer builds.

Final Debug and RelWithDebInfo runs pass **477/477 client-core checks**, **89/89 window checks**, **29/29 CPU renderer checks**, and **8/8 allocation-fault checks**. The existing lower-level pixel, deadline, input, command and lifecycle suites remain included. Independent source/test review closed with no remaining blocking findings after strengthening transactional rejection and failed-presentation coverage. Default-OFF target absence and dedicated binary fingerprint checks pass; this milestone does not claim a new combined live-server run.

The final Debug real-X11 cadence experiment observes 60 ticks over 0.9984 seconds idle and 0.9633 seconds during 924 XTest motions (901 actual callbacks), above the 0.944-second minimum for 59 intervals. Hoisting the pixel span out of the clear loop removed unnecessary per-pixel accessor overhead seen in the initial Debug/QEMU experiment. These observations validate pacing under events, not a game-rendering performance guarantee.

Final X11 runs pass in both configurations: actual XGetImage reads RGB (64,128,191) across all sampled regions at three window sizes, verifies the shared producer trace, and retains input/focus/relative-capture/close/signal coverage.
