## Next implementation sequence

1. **Observe the new hosted job after publication.** Fix any runner/platform
   regression before broadening renderer integration. Local results are not a
   substitute for hosted evidence.
2. **Design and implement one engine-facing native D3D9 boundary.** DXVK Native
   i386 calling conventions/header types differ from the engine's Win32-compatible
   declarations. Do not erase global stdcall or leak native DXVK types into
   serialized asset/VM structures. Establish a deliberate translation-unit/build
   boundary and retain 32-bit layout checks.
3. **Static genuine map view through the engine renderer.** Bring up real renderer
   initialization, asset/resource creation, BSP visibility/batching and enough
   material/pass coverage to draw a fixed map view. Preserve fail-closed unsupported
   cases; the standalone two-profile success is not general shader coverage.
4. **Continuous free-camera traversal.** Integrate real frame ownership, camera and
   input, then broaden models, effects, transparency, shadows and post-processing;
   test resize/reset/reload/shutdown against the reference scenes.
5. **Player spawn/connected gameplay.** Complete client/cgame startup, memory and
   entity services, prediction/snapshots, audio and the authentication boundary.
   Keep native Steam verification explicitly unfinished until implemented/tested;
   do not silently weaken admission to make a client appear connected.

A static map view is the next acceptance target, not a promise that spawning is
only a few functions away. Rendering API migration alone will not improve visual
quality. Preserve faithful-original tests first; enhanced shadows, antialiasing,
materials or lighting should become explicit optional features with their own
hardware/assets/visual acceptance criteria, rather than replace the reference.
